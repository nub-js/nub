Nub sizes libuv's threadpool to the cores of the machine it runs on, and runs the threads beyond Node's four at a lower priority, so a busy host does not pay for them.

Node hands async `fs`, `dns.lookup` (so every `fetch` to a new host), async `zlib` and async `crypto` calls to a pool of four threads, whatever the machine. Native addons such as `bcrypt` and `sharp` queue on the same four. On a 16-vCPU box, a login route that hashes passwords runs on four of the sixteen cores.

## The threadpool

Node's I/O library, libuv, keeps a pool of worker threads for the calls that block. The default is four threads, on a laptop and on a 64-core server alike. The size is read from `UV_THREADPOOL_SIZE` the first time the pool is used, so nothing inside the program can change it. The usual fix is a line in a Dockerfile or a systemd unit:

```bash
UV_THREADPOOL_SIZE=16 node server.js
```

Most deployments never set it. The pool stays invisible until a route that hashes passwords or resizes images shows up in a flame graph.

Nub sets the variable when it starts Node, on every launcher: the direct file run, `nub run`, `nubx`, `nub watch` and lifecycle scripts. The value is the larger of four and the cores available to the process, so a container gets its cgroup quota rather than the host's core count.

## Node's own attempt

In January, a member of Node's performance team proposed the same default for Node itself. The pull request collected eight approvals over six months.

The author closed it in August.

A pool sized to the host takes every core available, and on a box shared with other processes, or with the Node process's own event loop, that is a regression for everyone else. The thread also reports a file-read benchmark at −15% with sixteen threads on 16 vCPU, and on Windows each pool thread commits about 8 MB of stack. None of that disputes the size. The objection is to taking the cores unconditionally.

## The mitigations

The size is the one Node's team proposed, and three things around it answer the objections.

**Extra threads run at nice 10 on Linux.** Node's four keep their normal priority. Workers five and up get the nice level Chromium uses for its background threads, so the kernel runs them on otherwise idle cores and preempts them when other work arrives. On an idle box the pool runs at full width, and on a busy one it falls back toward Node's four.

/>

The same twelve processes beside a sixteen-thread pool at normal priority lose 7.5% of their throughput, and the server handles 37 requests a second. At nice 10 they lose about 1%, the server still serves more than plain Node, and the idle number is unchanged.

**Children keep Node's default.** A `cluster` worker, a PM2 fork or any `child_process` spawn starts with Node's four threads, because Nub removes its own value from `process.env` once the pool exists. Eight workers each carrying a sixteen-thread pool is the oversubscription raised upstream. A child that runs through `nub` is sized again. A value you set yourself, in the shell or in an env file, inherits as it does under Node.

**Windows stops at eight.** Each pool thread commits its full stack up front there, so the pool is capped instead of sized to the machine.

## The gain by core count

The multiplier tracks physical cores. An 8-vCPU box is four physical cores on the cloud shapes measured. Node's four threads already cover that hardware, so doubling the pool adds less.

  caption={<>The same routes on a c3d-standard-8 (8 vCPU, 4 physical cores), same method (<a href="https://github.com/nubjs/nub/blob/main/tests/bench/runtime/pool-bound.sh">benchmark</a>).</>}
/>

Compression is the weakest row on both boxes. A 1 MB gzip response is bound by the bytes moving through the event loop and the load generator as much as by the pool, so more threads help less. Routes that touch the pool lightly barely move. Five interleaved rounds of a 270 KB file read, a `stat` and a 55 KB gzip on the 16-vCPU box read within noise of plain Node. A burst of 400 `dns.lookup` calls finished in 59 ms instead of 84 ms.

## Opting out

An explicit `UV_THREADPOOL_SIZE` is used as is. Running under `nub --node`, or with `NODE_COMPAT=1` in the environment, leaves the pool at Node's default, along with the rest of what Nub adds.

The change is in [nubjs/nub#919](https://github.com/nubjs/nub/pull/919) and ships with the next release.
